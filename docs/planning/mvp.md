# MVP 계획

> 담당: PM · 최종 수정: 2026-11-21
> 출처: MVP 계획 (Notion)

12월 말까지 만들 **개발 범위와 완료 기준**을 적는다. 제품 요구사항(PRD)과 사업 정보는 Notion에 두고, 저장소에는 개발에 필요한 범위만 둔다.

---

## 1. MVP 목표와 완료 정의

12월 말까지 **"가입 → 첫 진단 → 사이드바 점검 → 세분화율 확인"이 실제 데이터로 끝까지 동작하는 상태**를 만든다. 이 흐름이 돌아가야 PRD(Notion)의 단일 검증 질문("세분화 훈련이 사용자의 질문 역량을 끌어올리는가")에 답할 데이터가 쌓이기 시작한다.

| 항목 | 내용 |
| --- | --- |
| 검증 질문 | 세분화 훈련이 실제로 먹히는가? (PRD 1단계) |
| 핵심 지표 | 자발적 세분화율 — 되묻기 전 첫 프롬프트의 형식 요소 충족률 |
| 기간 | 2026.11.19 ~ 12월 말 (1주 스프린트 6회) |
| 대상 사용자 | 1차 페르소나(김도현) 성격의 팀·지인 테스트 사용자 |
| 채널 | 크롬 확장 사이드바 + 웹(가입·온보딩·대시보드) |

**MVP 완료 정의 (모두 충족해야 완료)**

- 새 사용자가 크롬 확장 설치 후 웹에서 가입·온보딩을 마치고 첫 레벨을 받는다.
- 사이드바 입력창에 실무 프롬프트를 붙여넣으면 점검(부족한 조건 안내 → 되묻기 → 재작성)이 끝까지 동작한다.
- 형식 요소 판정과 충족률 계산이 실제 LLM 호출로 동작하고, 매 건 로그 필수 항목이 DB에 쌓인다.
- 웹 대시보드에서 현재 레벨과 세분화율, 회차별 추이를 볼 수 있다.
- 배포된 환경에서 팀원 외 테스트 사용자 5명 이상이 위 흐름을 마친다.
- 런칭 전 채점기 신뢰도 검증(같은 답변 5회 반복 채점, 항목별 일치율 90% 이상)을 통과한다.

## 2. 범위 — 우선순위

6주 안에 끝까지 동작하는 흐름을 만드는 것이 목표라, 핵심 지표의 데이터를 만드는 기능(가입·온보딩, 채점 엔진, 점검)을 Must로 두고 나머지는 단계적으로 붙인다.

| 우선순위 | 기능 | 이유 |
| --- | --- | --- |
| **Must** | 0. 계정·온보딩 (구글·이메일 가입, 약관, 닉네임, 온보딩 필수) | 사용자 식별과 기준선 측정 없이는 성장을 잴 수 없음 |
| **Must** | ① 진입 진단 = 웹 온보딩 (고정 문제 → 속성 선택 → Before/After → 이유 → 레벨 결과) | 첫 레벨과 기준선(before) |
| **Must** | 채점 엔진 (형식 요소 판정 1회 + 충족률 계산 + 모호표현 검출) | 세 모드 공통. 모든 기능이 이 엔진을 씀 |
| **Must** | ④ 실무 점검 (사이드바 기본값, 개방형 되묻기 → 재작성) | 핵심 지표의 주 데이터 출처, 실사용 빈도 최고 |
| **Must** | 로그 필수 항목 저장 (`rubric_version`·`domain`·`language` 포함) | 빠지면 이후 데이터 전체를 못 씀 |
| **Should** | 사이드바 진단 재측정 (선택형 되묻기 → Before/After → 레벨) | 레벨 변화 확인. 온보딩 진단과 같은 엔진 재사용 |
| **Should** | 웹 대시보드 최소판 (레벨, 세분화율, 회차별 추이, Before/After 기록) | 성장 가시화. 코드 계산값만 노출 |
| **Could** | 회고 (본인 과거 프롬프트 다시 보기 + 준비된 연습 1개) | 검증 대상 아님. 데이터가 쌓인 뒤에야 의미 있음 |
| **Could** | hover 해설 (span 기반), 배지·다음 목표, 진단 재실행 되묻기 | 경험 개선. 엔진이 span을 반환하면 화면만 붙이면 됨 |
| **제외** | 졸업·스캐폴딩 페이드·재방문, 축2·3 레벨 반영, 요금제·결제, 영어, 레이더 차트, 단축키(Ctrl+I) | PRD 9장 비스코프 및 2단계 이후 |

**우선순위 운영 규칙**

- Must가 끝나기 전에는 Should·Could 작업을 시작하지 않는다.
- S4가 끝났을 때 Must가 남아 있으면 Should를 다음 버전으로 넘긴다.
- Could는 S5에 여유가 있을 때만 착수한다.

## 3. 기능별 명세와 완료 기준

각 기능의 완료 기준이 곧 Jira 이슈의 "완료" 조건이다. 화면은 Figma Wireframe 페이지, 에픽은 Jira KAN 기준이다.

### 3.1 계정·온보딩 (Must) — KAN-4 · BE, FE, 디자인

- **흐름:** 사이드바 첫 화면 [로그인] → 웹 새 탭 → 로그인 또는 회원가입(구글·이메일) → 약관 동의 → 닉네임(구글 가입 시) → 온보딩 → 가입 완료 → 사이드바 재오픈 안내
- **화면:** AUTH-01·02, WEB-AUTH-01, WEB-JOIN-01·02·02B, WEB-ONB-00~06

완료 기준

- 구글·이메일 가입 모두 `user_id`가 발급되고, 온보딩을 마쳐야 가입 완료 처리된다.
- 로그인 후 새로고침해도 세션이 유지되고, 사이드바와 웹이 같은 계정 상태를 본다.
- 로그인 유도 전에 사이드바에 입력한 프롬프트가 로그인 후 복원된다.
- 가입 흐름 화면에 프로그레스바로 단계가 표시된다.
- 온보딩 중간 이탈 사용자의 데이터도 버리지 않고 남는다.

### 3.2 진입 진단 = 웹 온보딩 (Must) — KAN-4, KAN-6 · FE, AI, BE

- **흐름:** AI 사용 목적(도메인 결정) → 자기신고 레벨 → 고정 문제에 프롬프트 작성 → 중요 속성 선택·상세 입력 → Before/After 답변 비교 → 선호 선택 → 이유 입력 → 레벨·강점·개선점 결과

완료 기준

- 도메인 선택값에 따라 진단 문제와 형식 요소 세트가 정해진다.
- 되묻기 전 원문 프롬프트가 별도 필드로 저장되고, 충족률로 레벨(Lv.1/2/3)이 계산된다.
- After 프롬프트에 사용자가 고르지 않은 조건이 들어가지 않는다 (조립 후 재판정으로 검증).
- Before/After 화면 전환은 시간이 아니라 답변 생성 완료 신호로 일어나고, 대기 중에는 로딩 상태가 보인다.
- 두 카드는 같은 크기·강조로 보이고, 선택값(`user_preferred_side`)이 저장된다.
- 이유 입력은 비워도 넘어갈 수 있다.
- 결과 화면에 "직접 입력한 실력 vs 실제 측정된 실력"과 강점·개선점 문장이 템플릿으로 표시된다.

### 3.3 채점 엔진 (Must) — KAN-6 · AI, BE

- **입력:** `mode, domain, task_id, prompt_text, selected_attributes`
- **출력:** 항목별 `{ present, span, evidence }`, 충족률, 레벨(진단일 때만), 강점·개선점·되묻기 문장 변수

완료 기준

- 공통 5요소(목적·대상·분량·형식·모호표현) 루브릭과 few-shot이 `rubric_v0.4` 이상으로 확정된다.
- LLM 호출은 프롬프트 1건당 1회, 온도 0, JSON 출력이다.
- 모호표현은 LLM 없이 사전·패턴 코드로 검출된다.
- 같은 답변 5회 반복 채점 시 항목별 판정 일치율 90% 이상이다 (도메인별로 측정).
- 진단·점검·회고가 같은 엔진을 호출하고, 엔진 안에 채널(사이드바·웹) 분기가 없다.

### 3.4 실무 점검 (Must) — KAN-5, KAN-6 · FE, AI

- **흐름:** 사이드바 입력창에 프롬프트 붙여넣기 → [코칭 받기] → 있는 것·없는 것 안내(원문 인용) → 자유서술 질문 → 사용자가 직접 재작성 → 재작성본 재판정 → 추가로 다듬을지 선택
- **화면:** Figma "프롬프트 점검받기 (크롬)" 섹션

완료 기준

- 별도 버튼 없이 입력창에 붙여넣으면 점검이 시작된다.
- 안내 문구는 평가어 없이 "있는 것 / 없는 것"을 원문 인용과 함께 알려준다.
- 서비스가 프롬프트를 대신 고쳐 쓰지 않고, 재작성은 사용자가 한다.
- 최초 프롬프트와 재작성본이 각각 판정·저장되고, 최초 프롬프트 충족률이 세분화율 데이터로 쓰인다.
- 레벨은 바뀌지 않는다.

### 3.5 사이드바 진단 재측정 (Should) — KAN-5, KAN-6 · FE, AI

완료 기준

- 하단 [프롬프트 진단받기] 버튼으로 화면 이동 없이 모드만 전환되고, 입력 중이던 내용이 유지된다.
- 온보딩과 같은 도메인 문제·같은 충족률 기준으로 레벨이 계산된다.
- 선택형 되묻기(속성 선택 → 보기 3개)와 Before/After, 결과 화면이 동작한다.

### 3.6 웹 대시보드 최소판 (Should) — KAN-7 · FE, BE

완료 기준

- 현재 레벨(측정 날짜 포함), 세분화율(최근 5회 평균), 회차별 추이 그래프가 보인다.
- 성장은 `최초 20% → 현재 62% (42%p 상승)`처럼 %p로 표기하고, 진단 3회 미만이면 절대값만 보여준다.
- 추이 그래프는 진단·점검 데이터만 쓰고 회고는 제외한다.
- 역량(상단)과 활동(하단) 영역이 시각적으로 나뉜다.
- Before/After 기록은 저장된 스냅샷을 그대로 보여주고 재채점하지 않는다.
- 사이드바의 "성장 현황 보러가기" 링크는 새 탭으로 열린다.

### 3.7 회고 (Could) — KAN-5 · FE, AI

완료 기준

- 본인 과거 점검·진단 기록을 불러와 빠진 항목과 회차별 변화를 보여준다.
- 기록이 없으면 준비된 연습 1개(빈칸 채우기, 빈칸은 문장 끝)를 제공한다.
- 레벨업 조건을 채우면 "진단으로 확인해볼까요?"로 연결하고, 회고에서는 레벨을 바꾸지 않는다.

## 4. 핵심 사용자 흐름 (데모 시나리오)

가입과 온보딩은 한 번 거치는 입구이고, MVP가 매일 돌아가는 곳은 사이드바 점검입니다. 진단 재측정·회고·대시보드는 점검에서 갈라져 나갑니다.


**데모 시나리오 (MVP 완료 확인용)**

1. 크롬 확장을 설치하고 사이드바를 연다. 첫 화면에서 [로그인]을 누른다.
2. 웹 새 탭에서 구글로 가입하고, 약관에 동의한 뒤 닉네임을 입력한다.
3. 온보딩에서 AI 사용 목적(마케팅)과 자기신고 레벨(중급)을 고른다.
4. 고정 문제에 평소대로 프롬프트를 쓰고, 중요 속성을 고른 뒤 Before/After 답변을 비교한다.
5. 결과 화면에서 "직접 입력한 실력: 중급 / 실제 측정된 실력: 초급"과 강점·개선점을 확인한다.
6. 사이드바를 다시 열고, 실무 프롬프트("신제품 인스타그램 홍보 콘텐츠 만들어줘")를 붙여넣는다.
7. 점검이 빠진 조건을 알려주고 질문을 던지면, 사용자가 프롬프트를 직접 다시 쓴다.
8. 웹 대시보드에서 레벨, 세분화율, 회차별 추이에 방금 기록이 반영된 것을 확인한다.
9. DB에서 3~7단계의 로그 필수 항목이 빠짐없이 쌓였는지 확인한다.

## 5. 파트별 산출물

각 파트가 MVP 완료까지 내야 할 산출물입니다. Jira 이슈는 이 단위로 등록하고, 해당 에픽에 연결합니다.

| 파트 | 산출물 | 에픽 |
| --- | --- | --- |
| 백엔드 | 인증 API(JWT·회원가입·로그인·토큰 재발급), 사용자·온보딩 데이터 저장, 로그 필수 항목 DB 스키마와 저장 API, 사이드바·웹 공용 DB 구조, 대시보드 조회 API(레벨·세분화율·추이·Before/After 기록) | KAN-4, KAN-7 |
| 프론트엔드 | 웹: 로그인·약관·회원가입·닉네임·온보딩·결과·대시보드 화면 / 크롬 확장: 사이드바 첫 화면·점검·진단 재측정(·회고) 화면, 로그인 전 입력 임시 보관, 생성 완료 신호 기반 로딩 처리 | KAN-4, KAN-5 |
| 생성형 AI | 형식 요소 루브릭과 few-shot(`rubric_v0.4`), 판정기 프롬프트와 span JSON 스키마, 모호표현 사전·규칙, 충족률·레벨 계산 로직, After 조립 제약과 사후 검증, 강점·개선점·되묻기 문장 템플릿, 신뢰도 검증 리포트 | KAN-6 |
| 클라우드 | 개발·QA·운영 환경 배포, CI/CD, LLM 호출 병렬 처리와 길이 상한 설정, 디자이너 QA용 테스트 환경 | KAN-8 |
| 디자인 | 크롬 화면 ID 정리(EXT-DIAG·CHK·RET), 점검·진단 재측정·대시보드 하이파이 화면, 로딩·빈 상태·오류 화면, 문구 통일(강점/개선점 등), 회고 명칭 확정 | KAN-5 |
| PM | 스프린트 계획·리뷰, Jira 이슈 정리(에픽 연결), 미결정 사항 결정 회의 진행, 테스트 사용자 모집 | — |

## 6. MVP를 막는 결정 사항과 리스크

### 6.1 S1 안에 정해야 하는 결정

아래 항목이 정해지지 않으면 채점 엔진과 온보딩 화면 개발이 시작되지 못합니다. (PRD v0.3 13장 기준)

- **축1 정의:** 형식 요소 충족률 채택 확정 (속성 개수 방식 폐기)
- **형식 요소 목록과 이름:** 공통 5요소 확정, "구조=형식", "독자=대상" 같은 이름 통일
- **온보딩 다중선택 vs 사이드바 단일선택:** 충족률 방식이면 UI는 그대로 두어도 됨 — 그대로 둘지 확정
- **온보딩 드릴다운 입력 방식:** 자유 입력 유지(LLM 판정 추가) vs 선택지
- **`기타` 도메인 처리:** 공통 요소만 판정 vs 가까운 도메인 재선택
- **사이드바·웹 DB 연동 구조:** 백엔드 설계안 공유
- **Before/After 답변 생성 방식:** 병렬 호출 + 길이 상한 + 완료 신호 기반 전환

### 6.2 리스크와 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| AI 기능 개발 이슈가 아직 없음 (KAN-5·6 에픽 비어 있음) | 핵심 기능(점검) 일정 전체 지연 | S1에 채점 엔진·점검 이슈를 먼저 등록하고 AI 파트 P0 작업 착수 |
| BE 인증 API 기한 초과, FE 남은 작업 9건이 같은 날 기한 | 가입·온보딩 연동이 S2를 넘김 | S1에서 기한 재설정, 인증 PR 리뷰를 최우선 처리 |
| 채점기 판정 편차 | 레벨·세분화율 신뢰도 하락 | 런칭 전 5회 반복 채점 검증, 기준 미달 항목은 루브릭 보강 |
| Before/After 답변 생성 지연 | 온보딩 이탈 | 병렬 호출, 길이 상한, 스켈레톤 화면 |
| LLM 호출 비용 증가 | 운영비 초과 | 판정은 1건당 1회 고정, 다중 샘플링은 검증 결과를 보고 결정 |
| 크롬 화면 미정리 (화면 ID 없음, 명칭 혼재) | FE 구현 시 화면 혼동 | S1에 화면 ID 부여, 점검·회고 섹션 이름 정리 |
| 테스트 사용자 부족 | 완료 정의(외부 5명) 미충족 | S4부터 지인·수강생 대상 모집 시작 |
